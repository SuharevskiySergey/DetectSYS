## Пробел текущей реализации

`PoseEvidence.owner_epoch` — supplied строка. Ledger сравнивает её с baseline, но не выдаёт владение и не запрещает второму controller писать ту же лапу. `_dispatching` защищает один Python adapter от повторного входа, а не native writers. NumericInputsAccepted и корректный SHA-256 плана также не предоставляют владение.

Следовательно, нельзя подключать setters к proposal и называть это синхронным исполнителем: остаётся конкуренция с обычным updater, возвратом/ретракцией и экспериментальным контроллером корпуса.

## Требуемые свойства будущего native owner

Ниже **предложение интерфейса**, не существующие Blueprint methods.

1. Владение выдаётся native-арбитром **на конкретный экземпляр лапы в конкретном мире**. Label/name не заменяют identity экземпляра. Actor recreation и смена world инвалидируют старые claims.
2. Каждый успешный claim/передача владения имеет новый generation/epoch. Старое подтверждение нельзя использовать после release/reclaim даже тем же controller.
3. При отказе claim текущий owner и принятые команды не меняются. Нельзя сначала сбросить чужие цели и затем отказать.
4. **Все** native пути изменения этой лапы проверяют одну ownership policy: обычный Tick, stage/joint/claw команды, emergency/retraction и экспериментальные helpers. Python-token без native enforcement не lock.
5. Проверка claim, actual before revision, geometry/contact validity и связанное применение целей должны быть одним согласованным native действием. Проверка токена в Python до отдельного setter не устраняет race.
6. After receipt содержит identity/epoch и новый native application revision. Счётчик увеличивается для реально применённого связанного обновления, не для полученного numeric request. Порядок событий и частичный отказ нельзя маскировать успешным receipt.
7. Contact probe revision/capture sequence имеют отдельный смысл; успешный write не подтверждает контакт. Геометрический датчик не удостоверяет силовую опору.
8. Нет неявного auto-reclaim, auto-resume или timeout-transfer: пока поведение не согласовано и не реализовано native, неизвестное владение означает отказ.

Восемь лап могут принадлежать разным действиям. Порядок захвата нескольких лап должен быть фиксирован, а откат неполного claim — без изменения чужих целей. Если для действия требуются четыре опоры, частичный захват двух не должен выглядеть как начало четырёхопорного манёвра. Это требование к будущей реализации, не готовая atomic multi-leg transaction.

## Role не равна owner и не равна опоре

- `Support`, `Free`, `Observe`, `Aim`, `Beam`, `Stab`, `Slash`, `Retracting` — роли из ТЗ, но одно поле role не сериализует native команды.
- Support intent не подтверждает actual contact, запас устойчивости, центр масс, трение или допустимость снятия другой лапы.
- Observe может быть доступен у втянутого/неработоспособного по движению глаза; это не право выдвигать лапу или стрелять из гнезда.
- Временная недоступность лапы из-за действия и потеря работоспособности из-за здоровья — разные причины; их нельзя объединять в один `busy` bool.

## Подтверждённые правила preemption и незаданные конфликты

| Ситуация | Уже утверждено в ТЗ | Чего не следует добавлять самовольно |
|---|---|---|
| Срочная потребность в лапе во время зарядки луча (§5.2) | Зарядка прерывается, выстрела нет, слот освобождается, новая 6-секундная перезарядка не начинается | Считать отмену зарядки подтверждённой опорой/готовым claim |
| Начат Stab/Slash, нужна опора (§6) | Удар завершается; компенсация другими лапами/корпусом | Прерывать удар только потому, что locomotion имеет больший числовой priority |
| Коррекция drop attack угрожает посадке (§7) | Прекращается коррекция, не сам начатый удар | Отменять всю атаку или автоматически отдавать атакующую лапу в опору |
| Здоровье лапы 0 (§10) | Рефлекторная ретракция, недоступность движения/атак, наблюдение может остаться | Утверждать конкретный precedence при одновременном незавершённом ударе: конфликт §6/§10 требует решения |
| Neutralized наступает в середине начатого удара (§6/§10) | В Neutralized нет атак/передвижения; главный глаз закрыт | Самостоятельно выбирать между мгновенным abort и завершением удара; переходное поведение не задано |
| Качение (§4.3) | Рукопашные атаки запрещены; отдельные лапы могут маневрировать; втянутые глаза не стреляют | Переключать режим, оставив конфликтующий attack owner, без согласованного handoff |

### Явные решения пользователя после подготовки таблицы

Пользователь выбрал **«Прервать и втянуть»** при 0 HP во время удара и **«Завершить начатые удары»** при достижении порога Neutralized. Эти решения обновляют две нерешённые строки таблицы выше:

1. **Отказ конкретной лапы сильнее её melee completion.** При 0 HP прекращаются её атака/поражающее действие, новые команды движения/атаки отвергаются, запрашивается безопасное рефлекторное втягивание. Нельзя сначала доиграть удар этой лапой или считать выданную retraction-команду подтверждённой сложенной позой. Безопасная траектория/при невозможности исполнения — отдельная реализация, не мгновенный reset transform.
2. **Порог нейтрализации допускает drain уже начатых ударов ещё работоспособных лап.** Новые атаки запрещаются при достижении порога; затем завершаются оставшиеся ранее начатые удары, после чего устанавливается полное Neutralized. Это переходная фаза, не атака из окончательного Neutralized. Если завершающая удар лапа сама получает 0 HP, применяется п.1: её удар прерывается и не блокирует переход бесконечно.
3. **Запрет обычного preemption melee сохраняется.** Срочный locomotion/support запрос сам по себе не отменяет работоспособный начатый удар. Исключение 0 HP не превращает любой request опоры в emergency abort.

Впоследствии пользователь выбрал **«После завершения ударов»** для главного глаза: текущее состояние глаза/антимагии сохраняется во время melee drain, после завершения ударов требуется закрытие/отключение. Это не отдельное разрешение открывать глаз или выбирать новое направление во время перехода. Если pending melee уже нет, ждать несуществующего удара не требуется, но фактическое закрытие всё равно должно быть подтверждено native-реализацией.

Для уже идущей beam-зарядки при пороге нейтрализации выбран ответ **«Пока не определять»**. Нельзя самовольно считать её разрешённой к финальному выстрелу или отменённой с конкретным cooldown. Beam-переход пока не реализовывать/не подключать; запрет новых атак остаётся. Существующее отдельное правило прерывания beam при срочной потребности в опоре не менялось.

Имя промежуточного состояния, beam cancellation/cooldown при neutralization и native recovery после сорванного втягивания остаются не определены. Требование окончательного Neutralized (главный глаз закрыт, антимагия выключена, нет движения/атак) сохраняется.

Решения внесены в `Task.md`, но арбитр/события урона/рефлекторное втягивание **не реализованы этим документом**. Новых проверок и запусков не было.

## Cancel, hold и release — разные операции

- Local Python hold только инвалидирует pending/sample.
- `CancelStageRedistribution` относится к конкретному экспериментальному controller и его допустимым состояниям; не останавливает любых writers тела/других лап.
- Release снимает контроль и может оставить прежние цели активными. Его нельзя использовать как stop перед передачей owner.
- Передача владения требует подтверждённого native состояния/целей и policy преемника. Нельзя скрывать оставшееся движение под новым epoch.
- При частичном применении/потере owner запрещено подтверждать actualPoseConfirmed или автоматически повторять command. Политика восстановления должна быть отдельно реализована и проверена; этот документ её не подменяет.

## Минимальные критерии будущего приёмочного этапа

Source-only damage policy требует явного supplied completion ID при исчезновении surviving melee из snapshot. Native implementation должна удостоверять фактическое завершение action/hit-window в том же owner/epoch, а не просто очищение active-ID поля. Нынешняя pure функция этого не подтверждает и не закрывает ownership gate.

Только после отдельного разрешения на проверки должны подтверждаться: competing writers отвергаются; stale epoch после release/reclaim отвергается; отказ claim не меняет цели; native application receipt не выдаётся на partial update; world/actor recreation инвалидирует claim; release не считается stop; отменённый Beam освобождает слот без нового cooldown; начатый melee не отбирается для опоры произвольным priority.

Это **перечень будущих проверок**, не добавленные/выполненные тесты. Numeric Blueprint validation, historical observer gate и синхронное применение остаются отдельными обязательными рубежами. Новые assets, методы арбитра или runtime connections этим документом не созданы.
